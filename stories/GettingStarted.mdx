# @armsolusi/pdf-viewer

A React PDF viewer with stamping and freehand annotation built in — pdf.js rendering and
pdf-lib export behind a single component.

Instead of assembling pdf.js, pdf-lib and a drag/resize library yourself and then owning
the coordinate maths between them, you render one component and call one method to get a
flattened PDF back.

Every page in this Storybook is live. Change the controls, drag things around, export a
document — it is the real component, not a screenshot.

## Install

```bash
npm install @armsolusi/pdf-viewer
```

That is the whole setup. **React 18 or 19 is the only peer dependency** — `pdfjs-dist`,
`pdf-lib` and the pdf.js worker all come with the package, so there is no worker URL to
wire up and no second install to remember.

The package is **ESM only** — there is no CommonJS build, because there could not be a
working one: pdfjs-dist v6 is itself ESM-only.

## The smallest working example

```jsx
import { useCallback } from 'react'
import { PDFViewer, usePdfViewer } from '@armsolusi/pdf-viewer'
import '@armsolusi/pdf-viewer/style.css'

export function SignDocument() {
  const viewer = usePdfViewer()

  const download = useCallback(async () => {
    const blob = await viewer.getFlattenedPDF()
    const url = URL.createObjectURL(blob)
    const link = document.createElement('a')
    link.href = url
    link.download = 'signed.pdf'
    link.click()
    setTimeout(() => URL.revokeObjectURL(url), 10_000)
  }, [viewer])

  return (
    <div style={{ height: '100vh' }}>
      <PDFViewer
        viewer={viewer}
        src="/contract.pdf"
        config={{ specimenAsset: '/signature.png', onDownload: download }}
      />
    </div>
  )
}
```

**`usePdfViewer()` is how you reach the viewer** — for imperative calls like the export
above, and for reading state. Pair it with `useViewerState(viewer, selector?)` to gate your
own buttons on `hasSpecimen` or `hasAnnotation`; see **Integration → Specimen vs
Annotation**. A `ref` still works and exposes a smaller subset of the same API.

**The viewer fills its container**, so give the parent a height. Every story here is
wrapped in an `80vh` box for exactly that reason.

## The one thing this library will not do for you

**It never saves the file.** `onDownload` is yours to implement. That is what makes
uploading the signed document — rather than downloading it — just as natural. See
**Integration → Submit gating**.

## The pdf.js worker

**There is nothing to configure.** pdf.js parses documents in a Web Worker, and that
worker ships inside this package; your bundler emits it as a separate file on its own,
fetched only when a document loads.

It is worth knowing why, because it constrains one thing. No library can portably ask a
bundler for the URL of a file inside a *dependency*: `?url` imports are Vite-only, and
`new URL('pkg/file', import.meta.url)` works on webpack but not Vite. A path relative to
one of the package's own modules is the only form both understand — so the worker has to
live here, and `pdfjs-dist` is pinned to an exact version, since pdf.js throws when the
worker and the API versions differ.

Pass `config.workerSrc` to override it with a copy you serve yourself, or
`config.workerPort` for a `Worker` you built.

In Next.js the viewer must be client-side: add `'use client'` and load it with
`dynamic(() => import('./Viewer'), { ssr: false })`.

## `src` accepts more than a URL

A URL string, `File`, `Blob`, `ArrayBuffer` or `Uint8Array`. The bytes are read once and
reused for export, so a file picked straight from a file input works, and exporting does
not depend on the URL still being reachable.

Note that `src`, `specimenAsset` and `stampAssets` are URLs the **browser** fetches, not
module imports, so your bundler never rewrites them. If your app is served under a
sub-path, a leading `/` resolves against the origin and 404s — use
`` `${import.meta.env.BASE_URL}assets/sign.png` ``, or import the image so the bundler
owns the URL.

## How your users will drive it

Two of these are not guessable, so they are worth knowing before you write your own help
text. **PDFViewer → Interactions** is a live playground for all of them.

- **Move** — drag it, anywhere on the object, text boxes included
- **Edit text** — **double-click** the box; `Escape` or a click away stops. A box that
  was just created opens ready to type, so "add text" needs no double-click
- **Resize** — drag a corner or edge handle
- **Rotate** — drag the round handle above the object; `Shift` snaps to 15°
- **Across pages** — drag an object onto another page and it is reassigned to it
- **Undo** covers everything, one step per gesture — a whole drag, or a whole typing
  session, rather than one step per keystroke

## Stamps and images are separate

The **stamp** control places images *you* configured (`specimenAsset`, `stampAssets`);
the **image** control lets the *user* bring in their own. Only stamps from `specimenAsset`
count towards `hasSpecimen` — a seal or an uploaded photo does not, which is what makes
"has this actually been signed?" answerable.

Drop `'image'` from `toolbar.displayActions` to forbid user uploads.

## About the sample document

The PDF in these stories is generated, not a real file, and is deliberately awkward:

- **page 1** — plain A4
- **page 2** — A4 carrying a `/Rotate 90` entry
- **page 3** — a different page size

Those three cases are what a viewer usually gets wrong. Rotation used to place exported
annotations in the wrong spot on page 2, and zoom-fit used to measure only page 1 and so
overflow on page 3.
